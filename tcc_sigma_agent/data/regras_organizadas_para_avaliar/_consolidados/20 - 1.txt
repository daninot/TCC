# Arquivo: A.yml
title: Kubernetes Audit - Suspicious Access to Secrets
id: 4b2f9d6e-8c3a-4f1b-9d2e-0a1b2c3d4e7f
status: experimental
description: Detects suspicious Kubernetes API server audit events that access or modify Secrets (reads, lists, watches, creates, updates, patches, deletes). Flags activity by unusual principals or high-frequency access which may indicate exfiltration, credential harvesting, or misuse of privileges.
author: Daniela
date: 2026-06-03
references:
  - https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/
  - https://commandk.dev/blog/guide-to-audit-k8s-secrets-for-compliance/
logsource:
  product: kubernetes
  service: apiserver
  category: audit
detection:
  selection_secrets_resource:
    requestURI|contains:
      - "/secrets"
    objectRef.resource: "secrets"
  selection_sensitive_verbs:
    verb:
      - "get"
      - "list"
      - "watch"
      - "create"
      - "update"
      - "patch"
      - "delete"
  selection_unusual_principal:
    user.username|not_in:
      - "system:serviceaccount:kube-system:default"
      - "system:serviceaccount:kube-system:metrics-server"
      - "system:serviceaccount:kube-system:heapster"
      - "system:serviceaccount:kube-system:prometheus"
      - "system:serviceaccount:default:default"
      - "system:admin"
      - "kube-admin"
  selection_high_frequency:
    CountByUser: ">5"
    Timeframe: "5m"
  selection_failed_reads:
    responseStatus.code:
      - 401
      - 403
  condition: selection_secrets_resource and selection_sensitive_verbs and (selection_unusual_principal or selection_high_frequency or selection_failed_reads)
fields:
  - timestamp
  - verb
  - requestURI
  - user.username
  - user.groups
  - sourceIPs
  - objectRef.namespace
  - objectRef.name
  - responseStatus.code
falsepositives:
  - Legitimate administrative or automation activity by newly deployed controllers or CI/CD service accounts (whitelist known service accounts)
  - Compliance scans or backup tools that enumerate secrets on schedule
level: high
tags:
  - k8s.audit
  - attack.credential_access
  - attack.exfiltration
  - detection.audit
notes: |
  - Tune by whitelisting known service accounts and automation principals.
  - Correlate with abnormal source IPs, unexpected namespaces, large numbers of secret reads, or subsequent lateral activity.
  - Capture full audit records and, if possible, correlate with kube-apiserver requestBody for create/update/patch events to inspect suspicious payloads.

# Arquivo: B.yml
title: Kubernetes - Sensitive Secret Access, Mutation, or Unauthorized Attempt in Audit Log
id: 2e7a4f93-6c18-4b57-a082-9d5e3c8b7a14
status: test
description: |
    Detects four security-relevant operations against Kubernetes Secret resources
    in the API server audit log, combining the audit event schema (apiserver-audit.v1)
    with compliance requirements (HIPAA, GDPR, PCI-DSS, CIS K8s Benchmark 5.1.5):

    1. selection_bulk_list (HIGH) — verb=list on secrets. Enumerates ALL secrets
       in a namespace or cluster. Rarely needed by applications (which GET specific
       secrets); almost always reconnaissance or an over-permissioned service account.

    2. selection_secret_get (MEDIUM) — verb=get on a specific secret. Creates the
       compliance audit trail required by HIPAA/GDPR: who accessed which credential
       and when. Generate alerts when the actor is a human user (not system:serviceaccount).

    3. selection_access_denied (COMPLIANCE) — responseStatus.code=403 on secrets.
       Captures unauthorized access attempts blocked by RBAC. Required for compliance
       reporting: proves access controls are working AND reveals who is probing.

    4. selection_mutation (AUDIT) — create/update/delete/patch on secrets. Full
       lifecycle audit trail: who created, rotated, or deleted credentials and when.

    CRITICAL: Configure audit policy to log secrets at Metadata level (not
    RequestResponse). At RequestResponse, the responseObject field contains the
    base64-encoded secret values — the audit log itself becomes a sensitive artifact.
    Metadata level captures all fields needed for this rule without value exposure.

    Recommended audit policy for secrets (AuditPolicy resource):
      - level: Metadata
        resources: [{group: "", resources: ["secrets"]}]
references:
    - https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/
    - https://commandk.dev/blog/guide-to-audit-k8s-secrets-for-compliance/
    - https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/
    - https://attack.mitre.org/techniques/T1552/007/
    - https://attack.mitre.org/techniques/T1613/
author: Security Team
date: 2026-05-25
tags:
    - attack.credential_access
    - attack.t1552.007   # Unsecured Credentials: Container API
    - attack.discovery
    - attack.t1613       # Container and Resource Discovery
logsource:
    product: kubernetes
    service: audit
    definition: |
        Kubernetes API server audit log. Configure AuditPolicy with level=Metadata
        for secrets (NOT RequestResponse — that exposes secret values in logs).
        Key fields: verb, objectRef.resource, objectRef.namespace, objectRef.name,
        user.username, user.groups, responseStatus.code, stage.
        Filter on stage=ResponseComplete for action-confirmed events only.
detection:
    selection_stage:
        # Only alert on completed actions — avoids duplicate events per request
        stage: 'ResponseComplete'
        objectRef.resource: 'secrets'
    selection_bulk_list:
        # Bulk secret enumeration — highest-risk recon action
        # Empty objectRef.name = listing all secrets, not fetching one specific secret
        verb: 'list'
    selection_secret_get:
        # Individual secret read — compliance audit trail for credential access
        verb: 'get'
    selection_access_denied:
        # RBAC denial — compliance: proves controls work; reveals unauthorized probing
        responseStatus.code: 403
    selection_mutation:
        # Lifecycle changes — create/update/delete/patch on secrets
        verb|in:
            - 'create'
            - 'update'
            - 'delete'
            - 'patch'
    filter_system_controllers:
        # kube-system controllers legitimately read/manage secrets
        user.username|startswith:
            - 'system:serviceaccount:kube-system:'
            - 'system:serviceaccount:cert-manager:'
            - 'system:serviceaccount:external-secrets:'
    filter_known_operators:
        # Populate with your org's known secret-management service accounts:
        # user.username|in:
        #     - 'system:serviceaccount:vault-agent-injector:vault-agent-injector'
        #     - 'system:serviceaccount:sealed-secrets:sealed-secrets-controller'
        user.username: null   # placeholder
    condition: selection_stage and
               (selection_bulk_list or selection_secret_get or
                selection_access_denied or selection_mutation)
               and not 1 of filter_*
fields:
    - verb
    - user.username
    - user.groups
    - objectRef.namespace
    - objectRef.name
    - responseStatus.code
    - sourceIPs
    - impersonatedUser.username
falsepositives:
    - Vault Agent Injector, External Secrets Operator, or Sealed Secrets
      controllers legitimately reading and mutating secrets (use filter_known_operators)
    - Helm deployments creating/updating secrets for chart values
    - Kubernetes operators managing TLS certificates via cert-manager secrets
    - CI/CD pipelines reading deployment credentials from secrets
level: medium

title: Access to Kubernetes Secrets
id: b39c87d4-fa23-4412-bc91-230985cbaef4
status: experimental
description: Detects when a user or service account queries or retrieves Kubernetes Secret objects. Adversaries frequently target secrets to harvest passwords, tokens, API keys, and certificates to facilitate lateral movement and privilege escalation within the cluster.
references:
    - https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/
    - https://commandk.dev/blog/guide-to-audit-k8s-secrets-for-compliance/
author: Security Operations Center
date: 2026/06/03
tags:
    - attack.credential_access
    - attack.t1552 # Unsecured Credentials
logsource:
    product: kubernetes
    service: audit
detection:
    selection:
        objectRef.resource: 'secrets'
        verb:
            - 'get'
            - 'list'
    filter_system_users:
        user.username:
            - 'system:apiserver'
            - 'system:kube-controller-manager'
            - 'system:kube-scheduler'
    filter_system_sa:
        user.username|startswith: 'system:serviceaccount:kube-system:'
    condition: selection and not (1 of filter_*)
falsepositives:
    - Automated CI/CD deployment pipelines, infrastructure-as-code controllers (e.g., ArgoCD, Flux), or monitoring agents (e.g., Datadog, Prometheus) running with legitimate read permissions to secrets.
    - Cluster administrators performing authorized maintenance or troubleshooting operations.
level: medium
