# Arquivo: A.yml
title: O365/Azure AD - Federated Domain Added (AADBackdoor / Golden SAML Persistence)
id: 9c4e7b21-3f85-4a68-d012-7a5f9c3e8d47
status: test
description: |
    Detects the addition or modification of a federated domain in Office 365 /
    Azure Active Directory, a critical persistence technique (T1136.003) that
    creates a backdoor allowing authentication AS ANY USER without knowing their
    password, bypassing MFA, and evading Conditional Access policies.

    Technique (Dr. Nestori Syynimaa / o365blog AADBackdoor):
      1. Attacker adds a custom domain to the tenant (any free domain will do).
      2. Converts it to Federated authentication using Set-MsolDomainAuthentication
         or Set-AADIntDomainAuthentication, providing a self-signed certificate
         controlled by the attacker.
      3. Azure AD now trusts SAML tokens signed by that certificate — issued by
         an attacker-controlled IdP — for any user in the tenant.
      4. Backdoor persists through password resets and MFA re-enrollment.

    Threat actor attribution: NOBELIUM (UNC2452, SolarWinds attackers) used this
    technique to maintain persistent access to compromised O365 tenants post-
    SolarWinds. CISA Alert AA21-008A and FireEye UNC2452 report document this TTP.

    Three selections cover the Exchange and Azure AD workload variants:
      selection_exchange   — Add-FederatedDomain in Exchange workload (Splunk primary)
      selection_aad_fed    — Set domain authentication / federation settings (AAD audit)
      selection_new_domain — Domain addition as a precursor signal (high sensitivity)
references:
    - https://research.splunk.com/cloud/e155876a-6048-11eb-ae93-0242ac130002/
    - https://o365blog.com/post/aadbackdoor/
    - https://www.fireeye.com/content/dam/fireeye-www/blog/pdfs/wp-m-unc2452-2021-000343-01.pdf
    - https://www.cisa.gov/uscert/ncas/alerts/aa21-008a
    - https://attack.mitre.org/techniques/T1136/003/
    - https://attack.mitre.org/techniques/T1484/002/
author: Security Team
date: 2026-05-25
tags:
    - attack.persistence
    - attack.t1136.003  # Create Account: Cloud Account (Splunk mapping)
    - attack.t1484.002  # Domain Policy Modification: Domain Trust Modification
    - attack.t1550.001  # Use Alternate Authentication Material: App Access Token (forged SAML)
logsource:
    product: m365
    service: audit_exchange
    definition: |
        O365 Management Activity API (sourcetype: o365:management:activity).
        Enable both Exchange and AzureActiveDirectory workload logging.
        Key fields: Operation, Workload, UserId, ClientIP, ModifiedProperties.
detection:
    selection_exchange:
        # Primary: Exchange workload federation domain addition (Splunk detection source)
        Workload: 'Exchange'
        Operation: 'Add-FederatedDomain'
    selection_aad_fed:
        # Azure AD workload variants — setting authentication to Federated
        # Triggered by Set-MsolDomainAuthentication / Set-AADIntDomainAuthentication
        Workload: 'AzureActiveDirectory'
        Operation|contains:
            - 'Set domain authentication'
            - 'Set federation settings on domain'
    selection_new_domain:
        # Precursor signal: new domain added to tenant before federation conversion
        # Noisy on its own; combine with selection_aad_fed in correlation for high confidence
        Workload: 'AzureActiveDirectory'
        Operation: 'Add domain to company'
    filter_verified_changes:
        # Suppress planned changes during approved maintenance windows.
        # Populate with known admin accounts authorized for federation changes:
        # UserId:
        #     - 'o365-admin@corp.com'
        #     - 'svc-federation@corp.com'
        UserId: null   # placeholder — replace with authorized admin UPNs
    condition: (1 of selection_*) and not filter_verified_changes
fields:
    - Operation
    - Workload
    - UserId
    - ClientIP
    - ModifiedProperties
    - OrganizationId
    - ResultStatus
falsepositives:
    - Legitimate planned addition of a federated domain for ADFS or 3rd-party IdP
      integration — these should be tracked in change management and suppressed
      via filter_verified_changes with authorized admin account UPNs
    - Migration from cloud-only to hybrid identity (first-time federation setup)
    - Mergers and acquisitions adding new federated domains for acquired orgs
level: high

# Arquivo: B.yml
title: Azure AD Application Credential Modification for Persistence
id: 5b6c31f4-3d08-41e9-bc84-aa02d8495a12
status: experimental
description: Detects when a new password credential (client secret) or certificate is added to an existing Azure Active Directory (Entra ID) application or service principal. Attackers frequently use this technique to establish stealthy persistence (backdoors) within an enterprise cloud tenant, allowing them to authenticate as the modified application later and potentially bypass Multi-Factor Authentication (MFA) controls.
references:
    - https://research.splunk.com/cloud/e155876a-6048-11eb-ae93-0242ac130002/
    - https://o365blog.com/post/aadbackdoor/
author: Security Operations Center
date: 2026/06/04
tags:
    - attack.persistence
    - attack.t1098.001 # Account Manipulation: Additional Cloud Credentials
logsource:
    product: azure
    service: auditlogs
detection:
    selection_operations:
        operationName:
            - 'Update application'
            - 'Update service principal'
            - 'Add service principal credential'
            - 'Update application - Certificates and secrets management'
    selection_details:
        # Looking for indications of credential updates within the modified properties block
        properties.targetResources|contains:
            - 'KeyDescription'
            - 'PasswordCredential'
            - 'CredentialKey'
    condition: all of selection_*
falsepositives:
    - Legitimate cloud administrators or DevOps engineers rotating expired application secrets or updating deployment certificates.
    - Automated CI/CD pipelines or service accounts (e.g., Terraform, Ansible) managing infrastructure-as-code deployments.
level: high

# Arquivo: E.yml
title: Azure AD OAuth / Application Consent Abuse Detected
id: 2b7f4c9e-2026-0001-0000-00000000a1b2
status: experimental
description: Detects suspicious Azure AD / Office 365 audit events consistent with OAuth application consent abuse or malicious app registrations (user or non-admin created applications, service principals, or OAuth permission grants with external redirect URIs or non-standard owners). These behaviors are commonly used to establish persistence, exfiltrate data, or escalate access via malicious OAuth apps (AAD backdoor patterns).
author: Security Analyst
date: 2026-06-04
references:
  - https://research.splunk.com/cloud/e155876a-6048-11eb-ae93-0242ac130002/
  - https://o365blog.com/post/aadbackdoor/
logsource:
  product: azure
  service: azuread
  category: audit
detection:
  selection_app_registration:
    OperationName|contains:
      - "Add service principal"
      - "Add application"
      - "ApplicationRegistered"
      - "Add application"
      - "Create application"
  selection_oauth_grant:
    OperationName|contains:
      - "Consent to application"
      - "Add OAuth2PermissionGrant"
      - "Add delegated permission"
      - "Grant consent"
  selection_non_admin_actor:
    InitiatedBy.user.userPrincipalName|not_in:
      - "REPLACE_WITH_TRUSTED_ADMIN_1@example.com"
      - "REPLACE_WITH_TRUSTED_ADMIN_2@example.com"
      - "REPLACE_WITH_SERVICE_ACCOUNT_1@example.com"
  selection_external_redirect:
    TargetResources|contains:
      - "replyUrls"
      - "redirectUris"
    TargetResources|contains_any:
      - "http://"
      - "https://"
    TargetResources|contains_not:
      - "your-org-internal-domain.com"
  selection_high_priv_scope:
    TargetResources|contains_any:
      - "Directory.Read.All"
      - "User.Read.All"
      - "Mail.Read"
      - "Mail.ReadWrite"
      - "Files.Read.All"
      - "Files.ReadWrite.All"
      - "offline_access"
  condition: (selection_app_registration and selection_non_admin_actor and selection_external_redirect) or (selection_oauth_grant and selection_non_admin_actor and selection_high_priv_scope)
fields:
  - "@timestamp"
  - OperationName
  - InitiatedBy.user.userPrincipalName
  - InitiatedBy.user.id
  - TargetResources
  - Result
  - ClientIP
  - UserAgent
  - CorrelationId
falsepositives:
  - Legitimate developer or DevOps application registrations and consent flows initiated by non-admins (internal dev/test apps)
  - Third-party SaaS onboarding where users are allowed to consent to high-privilege scopes by policy
level: high
tags:
  - cloud.azure
  - cloud.office365
  - attack.credential_access
  - attack.persistence
  - attack.t1078
notes: |
  - Replace trusted admin/service account entries with your environment's allowlist.
  - Tune by excluding known CI/CD, onboarding, or SaaS integration service principals.
  - Investigate matched events by capturing the full audit record, reviewing the app's owners, reply/redirect URIs, granted scopes, and any subsequent token issuance or sign-ins by the app.
  - Recommended response: revoke consent for suspicious apps, remove service principals, rotate affected credentials, and perform tenant-wide token revocation if compromise is confirmed.
