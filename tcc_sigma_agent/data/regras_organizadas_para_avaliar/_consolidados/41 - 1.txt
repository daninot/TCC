# Arquivo: C.yml
title: Spring Security StrictHttpFirewall RequestRejectedException - Active Web Probing Detected
id: a73f2e18-9b4c-4d05-bc61-5e8d0c3f47a2
status: experimental
description: |
    Detects Spring Security's StrictHttpFirewall emitting RequestRejectedException
    log entries, indicating that an inbound HTTP request was rejected for containing
    a potentially malicious payload, forbidden characters, or a disallowed HTTP method.

    CLASS HIERARCHY CONTEXT (Spring Security 7.0.0 API):
    The relevant class tree from org.springframework.security.web.firewall is:

      java.lang.Object
      └── java.lang.Throwable
          └── java.lang.Exception
              └── java.lang.RuntimeException
                  └── org.springframework.security.web.firewall.RequestRejectedException
                          (thrown by StrictHttpFirewall, DefaultHttpFirewall)

    StrictHttpFirewall is Spring Security's default firewall since Spring Security
    4.2.4 / Spring Boot 2.x. It inspects every incoming request before the filter
    chain and rejects requests that contain:
      - Path traversal sequences (/../, /./, %2F, %2E%2E)
      - Double-encoded characters (%252F → decoded %2F → decoded /)
      - Illegal percent-encoded characters (%00, %0D, %0A — null byte, CRLF)
      - Semicolons in the path (;jsessionid= session fixation vectors)
      - Backslashes in the URL path (Windows path separator confusion)
      - Non-normalised paths (//path, /path//resource)
      - HTTP methods not in the configured allowlist (TRACE, DEBUG, TRACK,
        arbitrary custom verbs used in HTTP verb tampering attacks)
      - Invalid header characters (CRLF injection: \r\n in Host, X-Forwarded-For)

    When StrictHttpFirewall rejects a request, it throws RequestRejectedException,
    which Spring's HttpFirewallFilter catches and logs at WARN level via the SLF4J
    logger named:
        org.springframework.security.web.firewall.RequestRejectedException
    with a standardised message prefix:
        "The request was rejected because the URL contained a potentially
         malicious String"
    or (for method violations):
        "The request was rejected because the HTTP method was not included
         within the list of allowed HTTP methods"
    or (for header violations):
        "The request was rejected because the request header value was not allowed"

    ATTACK RELEVANCE:
    Each rejection category maps directly to a documented attack class:

    Path traversal / double-encoding  →  T1055, T1190 (directory traversal,
                                          LFI, RFI probing)
    Semicolon / jsessionid injection  →  T1550.004 (session fixation)
    Null byte / CRLF injection        →  T1134 (log injection, header splitting)
    Backslash path confusion          →  T1190 (IIS-style path confusion on
                                          reverse-proxied Spring apps)
    Disallowed HTTP method (TRACE)    →  T1040 (XST – Cross-Site Tracing,
                                          credential sniffing via TRACE reflection)
    Double-encoded sequences          →  T1036 (WAF/filter bypass by encoding)

    A burst of RequestRejectedException entries from a single source IP within a
    short window is a high-confidence indicator of automated scanner activity
    (Nikto, Burp Suite active scan, nuclei, sqlmap --level 5) or a manual
    attacker systematically probing filter bypass vectors.

    LOG FORMAT (Spring Boot default Logback/Log4j2 appender):
      WARN  o.s.s.w.f.RequestRejectedException - The request was rejected because
            the URL contained a potentially malicious String "%2F"

    or with request context (if RequestRejectedHandler is configured to log):
      WARN  o.s.s.w.firewall.StrictHttpFirewall - Rejecting request due to:
            The request was rejected because the URL...

references:
    - https://docs.spring.io/spring-security/site/docs/current/api/overview-tree.html
    - https://docs.spring.io/spring-security/site/docs/current/api/org/springframework/security/web/firewall/RequestRejectedException.html
    - https://docs.spring.io/spring-security/site/docs/current/api/org/springframework/security/web/firewall/StrictHttpFirewall.html
    - https://docs.spring.io/spring-security/reference/servlet/exploits/firewall.html
    - https://owasp.org/www-community/attacks/Path_Traversal
author: Generated from Spring Security 7.0.0 API class hierarchy (org.springframework.security.web.firewall)
date: 2024-01-01
tags:
    - attack.initial_access
    - attack.t1190       # Exploit Public-Facing Application
    - attack.reconnaissance
    - attack.t1595.002   # Active Scanning: Vulnerability Scanning
    - attack.defense_evasion
    - attack.t1027.001   # Obfuscated Files or Information: Binary Padding (encoding bypass)
    - attack.t1036       # Masquerading (HTTP method/path confusion)
    - tlp:white
logsource:
    category: application
    product: java
    # Spring Boot application log (Logback, Log4j2, or JUL) shipped via:
    #   - Filebeat / Fluentd tailing the Spring Boot log file
    #   - CloudWatch Logs / GCP Cloud Logging stdout capture
    #   - ECS / Kubernetes pod log aggregation
    #
    # The logger name in the log record will be one of:
    #   org.springframework.security.web.firewall.RequestRejectedException
    #   org.springframework.security.web.firewall.StrictHttpFirewall
    #   org.springframework.security.web.FilterChainProxy  (in older versions)
    #
    # Ensure your log shipper preserves the logger_name field for Arm 1.
    # If your SIEM flattens all fields into a single message string, Arm 2
    # provides message-content matching as a fallback.
detection:
    # ── Arm 1: Logger name match (highest specificity) ────────────────────────
    # The RequestRejectedException is always logged by a Spring Security firewall
    # logger. This logger name cannot appear in any legitimate application log
    # outside of a rejected request context.
    selection_logger_name:
        logger_name|contains:
            - 'springframework.security.web.firewall'
            - 'springframework.security.web.FilterChainProxy'
        level: 'WARN'

    # ── Arm 2: Message content — URL/path rejection strings ──────────────────
    # The standardised message prefix emitted by StrictHttpFirewall for all
    # path-based rejections. Stable across Spring Security 4.2.4 through 7.0.0.
    selection_url_rejection_message:
        message|contains:
            - 'The request was rejected because the URL contained a potentially malicious String'
            - 'The request was rejected because the URL was not normalized'
            - 'The request was rejected because the URL contained an invalid character'

    # ── Arm 3: Message content — HTTP method rejection ────────────────────────
    # Emitted when an HTTP method not in StrictHttpFirewall's allowed set is used.
    # Default allowed methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT.
    # Rejection of TRACE, DEBUG, TRACK, or arbitrary custom verbs fires this.
    selection_method_rejection_message:
        message|contains:
            - 'The request was rejected because the HTTP method'
            - 'was not included within the list of allowed HTTP methods'

    # ── Arm 4: Message content — header value rejection ───────────────────────
    # Emitted for CRLF injection attempts (\r\n) in header values, or other
    # characters blocked by StrictHttpFirewall's header validation.
    selection_header_rejection_message:
        message|contains:
            - 'The request was rejected because the request header value was not allowed'
            - 'The request was rejected because the HTTP header value contained'

    # ── Arm 5: Exception class name in stack trace ────────────────────────────
    # If the application's exception handler logs the full stack trace (common
    # when RequestRejectedHandler is not configured and the exception propagates
    # to the container's error page), the class name appears in the log body.
    selection_exception_classname:
        message|contains:
            - 'RequestRejectedException'
            - 'org.springframework.security.web.firewall'

    # ── Filter: expected security scanner traffic from approved tools ─────────
    # Populate with your DAST scanner and penetration testing source IP ranges.
    filter_approved_security_testing:
        c-ip|cidr:
            - '127.0.0.0/8'
            - '::1/128'
            # Add approved DAST / pen-test IPs here:
            # - '10.10.20.0/24'

    condition: >
        (
          selection_logger_name
          or selection_url_rejection_message
          or selection_method_rejection_message
          or selection_header_rejection_message
          or selection_exception_classname
        )
        and not filter_approved_security_testing

falsepositives:
    - Legitimate clients sending malformed requests due to a bug in their HTTP
      client library (e.g., double-encoding URLs before transmission). These
      produce isolated, low-volume rejections; distinguish from scanning by the
      absence of variety in the rejected string and a single consistent source IP.
    - Reverse proxies or CDNs that forward paths containing characters blocked by
      StrictHttpFirewall (e.g., paths with semicolons from certain load balancers).
      If this occurs consistently from a known proxy IP, add that IP to
      filter_approved_security_testing or override StrictHttpFirewall's
      allowSemicolon() setting.
    - Frontend SPAs that construct URLs with double slashes (//) due to a
      path-joining bug. These produce low-volume, consistent rejections from
      many different authenticated user IPs — easily distinguishable from scanner
      traffic by the authenticated session context and the repetitive path pattern.
    # Recommended SIEM threshold: alert when the same source IP produces
    # >= 5 distinct rejection messages within a 60-second window, which
    # separates systematic probing from accidental single-request mistakes.
    # Distinct rejection messages (e.g., path + method + header in same session)
    # from one IP is an immediate high-confidence indicator of manual testing.
level: medium

# ── Analyst correlation notes ─────────────────────────────────────────────────
# 1. Correlate with the web access log: StrictHttpFirewall rejection produces
#    HTTP 400 (Bad Request) or 500 at the container layer. A source IP generating
#    mixed 400s and 200s on adjacent requests confirms the attacker is alternating
#    between probe payloads and normal requests to map the filter boundary.
#
# 2. Check Spring Security's AuthorizationDeniedException log (also in the
#    org.springframework.security.access package) for the same source IP —
#    if both firewall rejections AND authorization denials occur together, the
#    attacker has already bypassed the firewall for some requests and is now
#    probing access control boundaries at the method-security layer.
#
# 3. The org.springframework.security.authentication package (also in the class
#    hierarchy) logs BadCredentialsException, UsernameNotFoundException,
#    LockedException at INFO/WARN. Combine with this rule for a compound
#    "scan + credential stuffing" alert when all three appear from one IP.

# Arquivo: D.yml
title: Spring Security Exceptions and Authentication/Authorization Failures
id: 8d2f1a6b-2026-spring-security-exceptions
status: experimental
description: Detects application log entries and web responses that reveal Spring Security exceptions, authentication/authorization failures, CSRF token issues, or stack traces referencing Spring Security classes. Useful for hunting authentication bypass attempts, misconfigurations, and information exposure in Spring-based applications.
author: Detection Engineer
date: 2026-06-07
references:
  - https://docs.spring.io/spring-security/site/docs/current/api/overview-tree.html
logsource:
  product: webserver
  service: application
  category: application_logs
detection:
  selection_spring_exception_names:
    Message|re:
      - '(?i)\bAccessDeniedException\b'
      - '(?i)\bAuthenticationException\b'
      - '(?i)\bBadCredentialsException\b'
      - '(?i)\bInsufficientAuthenticationException\b'
      - '(?i)\bAccountExpiredException\b'
      - '(?i)\bCredentialsExpiredException\b'
      - '(?i)\bDisabledException\b'
      - '(?i)\bLockedException\b'
      - '(?i)\bRememberMeAuthenticationException\b'
      - '(?i)\bInvalidCsrfTokenException\b'
      - '(?i)\bMissingCsrfTokenException\b'
      - '(?i)\bCsrfException\b'
      - '(?i)\bSessionAuthenticationException\b'
  selection_spring_stacktrace:
    Message|re:
      - '(?m)org\.springframework\.security\.[A-Za-z0-9_.\$]+\b'
      - '(?m)at\s+org\.springframework\.security\.[A-Za-z0-9_\.]+\('
  selection_http_status_authz:
    Status:
      - 401
      - 403
  selection_auth_endpoints:
    RequestUri|re:
      - '(?i)/login\b'
      - '(?i)/logout\b'
      - '(?i)/oauth/token\b'
      - '(?i)/oauth/authorize\b'
      - '(?i)/csrf\b'
      - '(?i)/actuator/health\b'
      - '(?i)/actuator/.*(env|configprops|mappings|beans)'
  selection_repeated_failures:
    CountByClientIP: ">5"
    Timeframe: "5m"
    Status:
      - 401
      - 403
  selection_stacktrace_in_response:
    ResponseBody|re:
      - '(?i)org\.springframework\.security'
      - '(?i)Traceback \(most recent call last\):'
      - '(?i)Exception in thread "'
  condition: (selection_spring_exception_names or selection_spring_stacktrace or selection_stacktrace_in_response) and (selection_http_status_authz or selection_auth_endpoints or selection_repeated_failures)
fields:
  - timestamp
  - Host
  - Service
  - ClientIP
  - HttpMethod
  - Uri
  - Status
  - UserAgent
  - Message
  - ResponseBody
  - Thread
falsepositives:
  - Normal application behavior where Spring Security intentionally logs authentication/authorization failures (e.g., legitimate failed login attempts).
  - Development or staging environments with verbose error pages or stack traces enabled.
  - Health checks or automated monitoring hitting auth-protected endpoints without credentials.
level: medium
tags:
  - web.application
  - spring
  - authentication
  - authorization
  - detection.logging
notes: |
  - Tuning: suppress alerts from non-production environments, known monitoring/health-check IPs, and scheduled automated scans; adjust repeated-failure thresholds to match baseline traffic.
  - Investigation: collect full request/response pairs, authentication context (username/account), recent deployment changes, stack traces, and correlate with other suspicious activity (credential stuffing, brute force, privilege escalation).
  - Mitigation: avoid exposing stack traces or internal class names to end users, enforce strong authentication controls, enable account lockout/rate limiting, validate CSRF protection configuration, and review Spring Security configuration for overly permissive rules.
